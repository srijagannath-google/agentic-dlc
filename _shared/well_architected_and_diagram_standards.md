## CRITICAL INVARIANTS (Enforced by `04/scripts/extract_contracts.py`)

1. **Separate Artifact per Architectural Perspective (`design/*_architecture.md`):**
   - Never cram all architectural perspectives into a single monolithic file. Each perspective (`business_architecture.md`, `high_level_solution_architecture.md`, `logical_architecture.md`, `application_architecture.md`, `data_architecture.md`, `security_architecture.md`, `infrastructure_architecture.md`) MUST be authored as its own focused, self-contained Markdown artifact under `design/`, and indexed by `design/architecture_design.md`.
2. **Flexible Multi-Layout Diagram Rendering (`gcp_diagram_renderer.py`):**
   - Never use one fixed diagram layout for every perspective. Each perspective uses its own purpose-built visual renderer in `04/scripts/gcp_diagram_renderer.py` (Chevron Capability Map, AI-Era 3-Tier Engagement/Intelligence/Record view with Persona Avatars, Concentric Multi-Zone Functional Topology, 4-Tier C4 Component Stack, 5-Stage Left-to-Right Data Pipeline, 5-Layer Defense-in-Depth Security Stack, and Multi-Region Hub-and-Spoke Infrastructure Topology).
3. **100% Cloud-Agnostic Architecture Diagrams (No Vendor Watermarks or Vendor-Locked Labels):**
   - **Never** render cloud vendor watermarks in the Business Capability Map or any other diagram.
   - **Never** title outer diagram containers `"Google Cloud"` — use cloud-agnostic titles (`Enterprise Target Architecture`, `Target Cloud / Hybrid Platform`, `Unified Intelligence, Agentic AI & Domain Data Platform`).
   - **Never** hardcode vendor-specific private VIP routes (`restricted.googleapis.com / 199.36.153.4/30`) or single-vendor product names (`Cloud Armor`, `Cloud CDN`, `Cloud Logging`) — use cloud-agnostic primitives (`Global L7 Load Balancer`, `Web Application Firewall (WAF)`, `Edge CDN`, `Zero-Trust OIDC Proxy`, `Virtual Router & NAT`, `Kubernetes Web & Application Tiers`, `Service Mesh mTLS`, `Private Service Route: internal.service.mesh 10.240.0.0/16`, `PgBouncer Pooler`, `Managed PostgreSQL HA Primary & Read Replica`, `Object Storage Buckets`, `KMS & Secrets Manager`, `Workload Identity`, `OpenTelemetry & Tracing`, `Metrics & SLO Alerting`, `GitOps & OPA Policy Engine`) aligned with `specs/target_stack.json`.
4. **Zero Spec/Design Trace Codes & Zero Raw JSON Blocks in Architecture Artifacts:**
   - **Never** include spec or design trace identifiers (`GRP-01`, `CAP-01`, `FRP-04`, `BR-01`, `REQ-FUNC-01`, `US-FUNC-01`, `Spec §3.3`) inside the 7 architecture perspective artifacts (`04/scripts/extract_contracts.py` fails Gate 4A if any trace code appears). Those trace IDs belong exclusively in `specs/application_spec.md` and `design/solution_design.md`.
   - **Never** embed raw ```` ```json ```` blocks inside the architecture artifacts.
   - **Never** expose internal script paths (`*.py`, `04/scripts/...`), plugin directories (`_shared/*.md`, `resources/reference_*`), subagent slugs, `SCENARIO_*` enum constants, `<details>`/`diagram-dsl` blocks, or raw `flowchart` Mermaid blocks in `design/*_architecture.md`, `design/architecture_design.md`, chat responses, or presentation artifacts. Keep the machine-readable `flowchart` specification in `design/diagrams/.specs/<perspective>.mmd` and embed **only** `![...](diagrams/<perspective>.png)` inside the published Markdown perspective files (keeping `sequenceDiagram` and `erDiagram` as live ```` ```mermaid ```` blocks).
5. **100% Target-State ("To-Be") — Zero Local-Testing Details in Design:**
   - Never put local testing mock flags (`APP_ENV=local`, `AUTH_MODE=local-mock`, `STORAGE_BACKEND=local-fs`, embedded SQLite fallback, `127.0.0.1` dev servers) into any file under `design/`.

## 1. Well-Architected Framework Pillars (Mandatory Cloud-Agnostic Design Baseline)

| # | Well-Architected Pillar | Architectural Focus | Mandatory Cloud-Agnostic Target Architecture & Design Practices |
| :-: | :--- | :--- | :--- |
| **1** | **System Design** | Modularity, Portability & Stateless Compute | • Partition business logic into modular, loosely coupled **Business Capability Services** and **AI Agent Services** deployed across a **Hub-and-Spoke Shared Virtual Network** topology.<br>• Keep web and application tiers **100% stateless** so workloads scale horizontally across primary and secondary regions with zero downtime.<br>• Select portable, open-standards platform primitives (`Kubernetes` containers, `PostgreSQL`-compatible relational database, `OpenTelemetry`) portable across On-Premises, GCP, AWS, and Azure. |
| **2** | **Operational Excellence** | Declarative GitOps & OpenTelemetry Observability | • Reconcile all target environments (`on-prem-gdc`, `gcp`, `aws`, `azure` / `prod`, `non-prod`, `dev`) declaratively via KRM GitOps (`Config Sync`) and enforce admission guardrails via `OPA Gatekeeper / Policy Controller`.<br>• Instrument every service with **OpenTelemetry (`OTLP`)** exporting traces, metrics, and structured JSON logs to centralized observability pipelines.<br>• Define SLIs, SLOs, and multi-window burn-rate alerts with automated rollback gates and operational runbooks. |
| **3** | **Security, Privacy & Compliance** | Zero-Trust Edge, Service Mesh mTLS, AI Trust Layer & Data Privacy | • **Zero-Trust Edge Perimeter:** Protect ingress with `Global L7 Load Balancer`, `Web Application Firewall (WAF & DDoS)`, `Edge CDN`, and `Zero-Trust Identity Proxy (OIDC)` verification before traffic enters the `Shared Virtual Network`.<br>• **AI Trust Layer & Zero-Leak DTO Boundary:** Enforce PII redaction before prompt assembly, prompt-injection defense, grounded RAG citation validation, and human-in-the-loop approval for state transitions (`_shared/zero_leak.md`).<br>• **Keyless Identity & Data Protection:** Use `Workload Identity (OIDC)` with least-privilege RBAC roles, `Service Mesh STRICT` mTLS, and `KMS` (`CMEK`) encryption at rest. |
| **4** | **Reliability** | Multi-Region Active-Active & Synchronous DB HA | • **Multi-Region & Multi-Zone Redundancy (`Primary Region` + `Secondary Region`):** Deploy stateless web and API tiers on `Kubernetes` across active-active regional pipelines (`Virtual Router & NAT` → `Web Tier` → `Compute Subnet`), backed by `PodDisruptionBudgets` and `HorizontalPodAutoscalers`.<br>• **High-Availability Persistence:** Configure the relational database tier (`Managed PostgreSQL HA`) with synchronous cross-zone standby failover, `PgBouncer` connection pooling, read replicas, and automated point-in-time recovery (`PITR`). |
| **5** | **Cost Optimization** | Shared Hub Infrastructure & Elastic Autoscaling | • Consolidate ingress, `NAT Gateway`, and shared security controls in the **`Shared Virtual Network`** while sharing subnets across capability services and persistence tiers to eliminate duplicate network infrastructure.<br>• Right-size container CPU and memory requests, autoscale elastically with Kubernetes HPA, co-locate compute and data tiers per region, and apply FinOps cost-allocation labels. |
| **6** | **Performance Optimization** | Edge Caching, Connection Pooling & Indexing | • Use `Edge CDN` and `Global L7 Load Balancing` in front of static web assets, `PgBouncer` connection multiplexing in front of `PostgreSQL HA`, B-Tree indexes on relational lookup columns, and asynchronous `OpenTelemetry` batch export. |
| **7** | **Environmental Sustainability** | Carbon-Aware Regions & Minimal Rootless Images | • Select high Carbon-Free Energy (`CFE%`) regions, use minimal multi-stage rootless OCI container images, and share hub infrastructure across services to minimize idle carbon footprint. |

## 2. First-Principles Failure Mode & Anti-Pattern Grilling (Mandatory in `design/infrastructure_architecture.md §2.2`)

Every Stage 4A `design/infrastructure_architecture.md` MUST challenge the target architecture against these 5 canonical failure vectors and document the concrete remediation in `§2.2`:

| Grilling Vector | Critical Challenge Question | Cloud Anti-Pattern Prohibited | Mandatory Cloud-Agnostic Target Architecture Remediation |
| :--- | :--- | :--- | :--- |
| **1. Blast Radius & Regional/Zonal SPOF** | If the primary region or a single compute zone fails, does the application remain available? | Single-region/single-zone deployment or stateful local-disk session storage. | Active-active `Primary Region` and `Secondary Region` pipelines inside `Shared Virtual Network` running stateless `Kubernetes` pods, backed by synchronous HA `PostgreSQL` standby failover. |
| **2. Ingress Exposure & Public IPs** | Do backend Kubernetes pods or database instances expose public IP addresses or traverse the public internet for internal APIs? | Public IP addresses on backend workloads/databases or unencrypted public internet routing for internal APIs. | `Virtual Router` advertises private service routes (`internal.service.mesh 10.240.0.0/16`, `#D93025` red dashed route); `Kubernetes` pods and `PostgreSQL` instances reside in private subnets with zero public IPs. |
| **3. Credential & Identity Security** | Are long-lived static service account keys or static DB passwords embedded in workloads? | Static credential files or hardcoded secrets in `ConfigMap` or container layers. | Keyless `Workload Identity (OIDC)` bound to least-privilege service accounts; secrets injected from `Secrets Manager` and encrypted at rest with `KMS (CMEK)`. |
| **4. Database Scalability & Connection Starvation** | When `Kubernetes` pods autoscale under peak load, will database connections saturate? | Direct unpooled database connections from autoscaling pods; unindexed full-table scans. | Managed `PgBouncer` connection pooling between `Kubernetes` pods and `PostgreSQL HA`, B-Tree indexes on foreign-key and status columns, and read-replica offloading. |
| **5. Environment Sprawl & Governance Drift** | Are workloads mutated manually via `kubectl` or deployed without policy guardrails? | Manual console/CLI drift; unverified privileged containers or missing RBAC/mTLS policies. | Declarative GitOps reconciliation via `Config Sync`, admission enforcement via `OPA Policy Controller`, and `Service Mesh STRICT` mTLS across all services. |

## 3. FinOps & Multi-Cloud TCO Sizing Estimation (`design/infrastructure_architecture.md §3`)

Every `design/infrastructure_architecture.md` SHOULD include a `§3 FinOps Workload Sizing & Multi-Cloud TCO Estimate` table (grounded by optional `cloud-finops` MCP pricing tools when connected, or transparent standard list-price assumptions otherwise) detailing:
1. **Right-Sized Tier Resource Envelope:** Stateless Web/UI pods (`vCPU`, `GiB RAM`, min/max HPA replicas), Stateless API/Domain pods, `PgBouncer` + `Managed PostgreSQL HA` (`vCPU`, `GiB RAM`, `IOPS`, HA storage GiB), Object Storage & Backup retention, and OpenTelemetry ingestion volume.
2. **Portable Environment Cost Matrix:** Estimated monthly steady-state run-rate across target environments (`on-prem-gdc`, `gcp`, `aws`, `azure`) with 1-year / 3-year committed-use optimization levers.
3. **Legacy Retirement Cost Offset (Modernization Scenarios):** Decommissioned legacy licensing, server hosting, and manual operational toil offset by each Strangler cutover wave.
